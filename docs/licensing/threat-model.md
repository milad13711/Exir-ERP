# مدل تهدید لایسنس — چه چیزی قابل جلوگیری است و چه چیزی نه

## حقیقت بنیادی
وقتی مشتری **سرور و دیسک را در اختیار دارد**، هر کدی که روی آن اجرا می‌شود قابل مشاهده، تغییر و اجرا در محیط دلخواه است. Node.js/TypeScript تفسیری است؛ حتی bundle/obfuscate شده هم با زمان و مهارت کافی بازگردانی یا patch می‌شود. هیچ لایه‌ی فنی «جلوگیری مطلق» نیست. هدف عملی ما:
1. **کپی/اشتراک ساده و اتفاقی را غیرممکن کنیم** (هزینه‌ی دور زدن را از «کپی پوشه» به «مهندسی معکوس مداوم» برسانیم).
2. **هر دستکاری را قابل‌تشخیص و قابل‌گزارش کنیم** (شواهد برای اجرای قرارداد).
3. **اعتماد را بر چیزی بنا کنیم که مشتری نمی‌تواند جعل کند** (امضای نامتقارن در سرور ما).
4. **لایه‌ی حقوقی** را پشتوانه‌ی فنی کنیم.

## آنچه جلوگیری می‌شود (با فرض مشتری عادی و حتی مشتری فنیِ متوسط)
| تهدید | اقدام |
|---|---|
| جعل لایسنس/توکن/پاسخ سرور | Ed25519: فقط کلید **عمومی** در محصول؛ ساخت توکن بدون کلید خصوصی ما ناممکن است (برخلاف HMAC مشترک مرجع که با استخراج راز قابل جعل بود) |
| ویرایش ماژول‌ها/سقف کاربر/تاریخ داخل توکن | امضا؛ هر بایت تغییر = رد |
| replay پاسخ قدیمی سرور (مثلاً «valid» قبل از ابطال) | `nonce` + پنجره‌ی ±۳۰۰ث + `serverTime`/`tokenExpiresAt` امضاشده |
| کپی دیتابیس/volume روی سرور دوم | اتصال به `installationId` + اثرانگشت میزبان (machine-id/CPU/کرنل/RAM/شبکه)؛ نصب دوم باید دوباره فعال شود و ظرفیت `maxActivations` مصرف می‌کند |
| استفاده‌ی هم‌زمان از یک کلید در چند سایت | سقف فعال‌سازی اتمیک (قفل ردیف)، گزارش IP/نسخه، آزادسازی فقط توسط ادمین یا deactivate |
| برگرداندن ساعت برای تمدید ظاهری | `lastSeen` ماندگار + `serverTime` امضاشده؛ زمان مؤثر = max(ساعت، lastSeen)؛ برگشت > ۷ روز = قفل تا check-in |
| تخمین/حدس کلید | کلید ≈ ۱۰۰ بیت آنتروپی، rate limit + قفل نمایی IP، یکسان‌سازی زمان، `not_found` یکسان |
| حمله به سرور لایسنس | کلید خصوصی رمزگذاری‌شده و بیرون از DB/git؛ ادمین فقط SUPER_ADMIN + 2FA؛ ردپای فقط‌افزودنی؛ ورودی‌های اعتبارسنجی‌شده و queryهای پارامتری؛ UI با React (escape خودکار) |
| ابطال/تعلیق نادیده گرفته شود | حکم امضاشده فوراً در check-in بعدی + CRL؛ حکم در state ماندگار است |
| تغییر سهوی/ساده‌ی کد (patch کوچک، فایل اضافه) | مانیفست امضاشده + راستی‌آزمای دوره‌ای + گزارش در check-in |

## آنچه نمی‌توان جلوگیری کرد (صادقانه)
| تهدید | چرا | کاهش اثر |
|---|---|---|
| **حذف/patch خود چک‌های لایسنس و راستی‌آزما** در JS | کد در محیط مشتری اجرا می‌شود؛ مهاجم می‌تواند `LicenseGuard`/`ModuleGuard`/`IntegrityService` را خنثی کند و مانیفست را هم دور بزند (چون کدِ تأییدکننده خودش تحت کنترل اوست) | چند نقطه‌ی کنترل پراکنده (سخت‌تر برای patch کامل)، bundle/minify، تلمتری (نسخه/کاربر/ماژول)، **قرارداد**، و اینکه بدون check-in/به‌روزرسانی ما، نسخه‌ی patch‌شده از پشتیبانی و نسخه‌های جدید محروم است |
| کلون کامل VM/Snapshot با machine-id یکسان | اثرانگشت دو کپی یکسان است | تشخیص مصرف هم‌زمان از IP/نسخه‌ی متفاوت در پنل؛ `maxActivations=1` + بررسی دوره‌ای؛ قرارداد |
| بازگردانی توکن + قطع دائمی اینترنت + ساعت ثابت | سیستم آفلاین فقط بر ساعت محلی تکیه دارد | عمر توکن محدود (پیش‌فرض ۱۴ + ۱۴ روز مهلت) → حداکثر ~۲۸ روز؛ توکن آفلاین عمر بلندتر دارد و صریحاً به نصب گره خورده |
| استخراج کد منبع از ایمیج | ایمیج حاوی JS است | تحویل **فقط ایمیج** (بدون سورس/git)، حذف sourcemap، minify (پایین)، قرارداد |
| اجرای ماژول‌های جداگانه در وب‌پنل بدون بک‌اند | بندل وب در مرورگر است | هر داده/عملی سمت **سرور** با `ModuleGuard` و توکن اعمال می‌شود، نه فقط پنهان‌کردن UI |
| مشتری دستور SQL مستقیم روی DB خودش بزند (`TenantModule`) | DB در اختیار اوست | `ModuleGuard` در on-prem مجوز را از **توکن امضاشده** می‌خواند، نه فقط از DB |
| سرقت کلید خصوصی ما | ریسک سرور لایسنس | رمزگذاری، secret file، CRL برای `kid`، چرخش، دفترچه‌ی حادثه (README §۵) |

## لایه‌های پیاده‌سازی‌شده
1. **توکن امضاشده + اعمال چندنقطه‌ای** (guard سراسری، `ModuleGuard`، سقف کاربر، توقف cron، بوت‌استرپ، sync ماژول‌ها).
2. **مانیفست یکپارچگی امضاشده** (SHA-256 تمام `dist`، بوت + دوره‌ای، گزارش در check-in، سیاست WARN/LOCK توسط توکن). پیش‌فرض WARN تا مشتری تصادفی قفل نشود (مثلاً پچ امنیتی دستی).
3. **تحویل فقط Docker image:** compose مشتری فقط `image:` دارد (نه `build:`)؛ در ایمیج سورس TS و sourcemap نیست. ایمیج نهایی فعلاً `node dist/main.js` است؛ **مسیرهای بیشتر (ارزیابی‌شده، فعلاً فعال نشده تا بیلد خراب نشود):**
   - *Bundle تک‌فایل با esbuild/`@vercel/ncc` + minify:* امن و سریع؛ ساختار پوشه‌ها را پنهان می‌کند. نیاز به تست NestJS (decorator metadata با esbuild مشکل‌دار است — در `bootstrap-on-premise.ts` هم همین هشدار هست؛ ncc/`tsc`+`terser` ایمن‌تر است).
   - *`terser` روی خروجی `tsc` (با `keep_classnames` و `keep_fnames` برای DI نست):* بدون بازنویسی؛ توصیه‌ی اول.
   - *`javascript-obfuscator`:* کند و بیش‌ازحد شکننده برای NestJS؛ توصیه نمی‌شود مگر روی فقط ماژول لایسنس/انتگریتی.
   - *V8 bytecode (`bytenode`):* سخت‌ترین مهندسی معکوس، ولی وابسته به نسخه‌ی Node/معماری و با decorator-metadata ناسازگار؛ فقط برای فایل‌های لایسنس در صورت نیاز آینده.
   - *وب‌پنل (Next.js):* `next build` خروجی minify می‌دهد؛ `productionBrowserSourceMaps` باید `false` بماند (پیش‌فرض)؛ ایمیج `standalone` بدون سورس؛ منطق مجوز حساس در بک‌اند باشد نه در بندل.
4. **قرارداد** (`license-terms-fa.md`): ممنوعیت تغییر/مهندسی معکوس/توزیع، حق ممیزی و گزارش، پذیرش تلمتری، پیامد نقض.
5. **تلمتری check-in** (حداقلی، بدون داده‌ی شخصی؛ README §۱۰).
6. **تعلیق/ابطال از راه دور** با پاسخ و CRL امضاشده.
7. **توکن‌های مقید به نصب با تمدید خودکار.**

## ریسک‌های باقی‌مانده و تصمیم‌ها
- اولین خط دفاع **حقوقی + ارزش افزوده** است (به‌روزرسانی، پشتیبانی، backup آفلاین، یکپارچه‌سازی): لایسنس دائمی با `updatesUntil` یعنی مشتری بدون تمدید پشتیبانی هم کار می‌کند ولی نسخه‌ی جدیدتر از تاریخ نمی‌گیرد (`updates_expired` برای build‌های بعد از آن تاریخ).
- سیاست LOCK برای مشتریان پرریسک؛ WARN برای بقیه.
- هرگز لایسنس را بدون گزارش/اخطار به‌صورت خودکار از «ابطال» ساعتی در شبکه‌های ناپایدار ایران قفل سخت نکنید؛ طراحی عمداً **آفلاین‌محور با مهلت** است.
- اگر ریسک سرقت IP بالاست، گام بعدی: اجرای بخش‌های حساس (مثلاً موتورهای محاسباتی ویژه) به‌صورت سرویس سمت سرور ما، نه در سرور مشتری.

## افزوده‌های بازبینی امنیتی
- **machine-id میزبان:** mount فقط‌خواندنی `/etc/machine-id` به پروسه‌ی backend اجازه می‌دهد شناسه‌ی میزبان را بخواند (فقط هش SHA-256 مصرف و ارسال می‌شود، مقدار خام نه). ریسک: کد مخرب داخل کانتینر هم آن را می‌خواند؛ جایگزین: حذف mount و تنظیم `HOST_MACHINE_ID` (اثرانگشت ضعیف‌تر).
- **چرخه‌ی activate/deactivate:** با نگه‌داشتن اسلات تا پایان اعتبار توکن بسته شد؛ هنوز مشتری می‌تواند ظرفیتش را با «انتقال واقعی» (آزادسازی ادمین) جابه‌جا کند.
- **CGNAT:** قفل IP کوتاه (≤۱۵ دقیقه) و با معافیت نصب‌های شناخته‌شده؛ سقف نرخ همچنان فعال است.
