# Application security audit — October 2026

Scope: `apps/backend-core` (NestJS API, control plane + DB-per-tenant), `apps/web-panel` (tenant UI + public no-login pages),
`apps/admin-panel` (platform super-admin UI), `apps/marketing-site`. Out of scope (other workstreams): backup/DR
(`src/settings/backup*`, `src/backup-dr`, `scripts/backup*`) and host hardening (`infra/hardening/`).
Method: code review with file:line evidence, targeted greps over every controller/DTO/PDF template/outbound `fetch`, dependency
audit, git-history secret scan, real Nest DI boot with a live HTTP pipeline (`npm run di:check`), unit tests for every fix.
Nothing was run against any non-local target.

Evidence lines refer to the **pre-fix** tree (`git show HEAD:<file>`).

## Threat model (short)

| Actor | Goal | Main entry points | Key controls (after this audit) |
|---|---|---|---|
| Anonymous internet user | Take over a tenant user / admin account | OTP login, admin login, public OTP flows | CSPRNG codes, per-phone + per-IP + global caps, guess lockout, admin lockout + TOTP, default-credential block |
| Anonymous internet user | Burn SMS budget (SMS pumping) / spam staff | `…/otp/request`, public forms, site forms | per-phone 5/15 min & 15/day, 30 s cooldown, global daily cap, IP limits, mail-form limits |
| Malicious tenant (or stolen tenant OWNER session) | Reach other tenants or platform internals | webhooks, PDF/HTML templates, uploads, `/platform` | tenant DB resolved only from token→control DB; SSRF guard; Chromium request blocking; active-content upload block |
| Malicious tenant employee | Escalate inside tenant | user/role/permission endpoints | hierarchy checks, disable really revokes |
| Anonymous → admin XSS | Steal admin token from `localStorage` | public form fields rendered in admin UI | URL validators + `safeHref`, JSON-LD escaping, report-only CSP |
| Compromised secret / leaked key | Persist access | JWT secret, API key, DB creds, gateway keys | epoch/tenant/member/admin token versions, revoke-all-keys, runbook, encrypted secrets at rest |
| Supply chain | Known CVEs | npm deps | `npm audit` fixes applied; remainder listed below |

Trust boundaries: browser ↔ nginx/CDN ↔ Next (SSR) ↔ API (`X-Real-IP` trusted only from private/loopback peers) ↔ control DB / tenant DBs
(one Postgres cluster, one superuser role — see S-14).

### Verified, no change needed
* **Tenant isolation:** `JwtAuthGuard` derives the tenant DB only from `payload.tenantId` → control-DB row; `tenantSlug`/`publicKey` URL segments are only used by public routes that re-resolve the tenant and bind tickets (`tenantSlug` claim). The `/platform` guard (`platform-owner.guard.ts`) requires a real user session of the platform tenant with OWNER/ADMIN (API keys excluded).
* **SQL injection:** all 7 raw queries are Prisma tagged templates (parameterised); `CREATE/DROP DATABASE` names pass a strict allow-list regex. **Command injection:** `execFile`/`spawn` use argument arrays with server-built values.
* **Global ValidationPipe** is `whitelist + forbidNonWhitelisted + transform` (no mass assignment).
* **CORS:** explicit origin allow-list with credentials for the app; wildcard without credentials only on `/api/public/forms/*`, with per-form origin checks.
* **CSRF:** bearer tokens in the `Authorization` header only; no cookies are set anywhere.
* **File serving / ReDoS / prototype pollution:** no user-controlled file paths, no `new RegExp(userInput)`, no deep-merge helpers.
* **Open redirects:** no `next=`/`returnUrl` parameters; payment redirects are built from server env + gateway responses.
* **Git history:** no committed private keys/tokens/passwords (only the dev placeholders in `*.example` and the seed password in S-01). No secrets are reproduced in this report.

## Rollout notes / risk register
1. **Migration `20261008100000_security_hardening`** (additive columns + `security_state`) runs automatically in `docker-entrypoint.sh` before the server starts. Deploy the backend first, then the frontends.
2. **First boot in production fails** if `JWT_SECRET` is missing/placeholder/<16 chars. Check the current value *before* deploying; a 16–31-char secret boots with a warning (rotate per runbook). Temporary escape: `ALLOW_WEAK_JWT_SECRET=true`.
3. **Admin console:** if `admin@exir.co`/`support@exir.co` still carry the repo-default passwords, login is refused until you rotate them with `create-admin-user` (S-01). This is intentional.
4. **Rate limits are enforcing by default** (generous: 30 OTP requests/IP/15 min, 60 public writes/IP/min…). If real users share one NAT or the CDN hides client IPs (all requests appear from the CDN IP) raise `RL_*` or start with `RATE_LIMIT_REPORT_ONLY=true` for a few days and read the `RATE_LIMITED` events on the admin "امنیت" page. **Verify nginx forwards the real client IP in `X-Real-IP` (use `real_ip_header` with ArvanCloud ranges), otherwise per-IP limits see the CDN.**
5. **CSP is report-only** for the three Next apps; promote to enforcing after reviewing reports (`CONFIG_INSECURE` INFO events).
6. **APP_SECRETS_KEY unset** keeps everything working (legacy plaintext still readable) but saving a *new* gateway/SMS key or enabling 2FA returns 503 until it is set. After it is set, existing keys are encrypted the first time they are read.
7. Tenant backups (`settings/backup`) export `module_settings`; encrypted values restore only with the same `APP_SECRETS_KEY` — keep it with the backup key (offline copy).
