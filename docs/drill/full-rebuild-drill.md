# تمرین بازسازی کامل (Full Rebuild Drill)

هدف: **اثبات عملی** اینکه فقط با سه چیز می‌شود کل پلتفرم را روی یک سرور تازه بالا آورد و زمان واقعی (RTO) را اندازه گرفت:
1. مخزن git
2. فایل `.env` و رازها که **خارج از سرور** نگه‌داری می‌شوند
3. بکاپ‌های رمزنگاری‌شده‌ی خارج از سرور (S3)

بکاپی که هرگز بازیابی نشده، فرض است نه واقعیت. این تمرین هر ۳ ماه (و بعد از هر تغییر بزرگ در زیرساخت/بکاپ) تکرار شود.
مرجع دستورهای دستی: `docs/disaster-recovery.md` §۵-ج. اسکریپت خودکار: `scripts/drill/rebuild-drill.sh`.

> **هرگز روی سرور تولید اجرا نکنید.** اسکریپت پیش‌فرض dry-run است، و بدون hostname شامل `drill`، تأیید صریح `DRILL_ALLOW_HOST`، نبودن نشانه‌های سرور تولید (`/etc/exir`، `/opt/exir-erp`، گواهی دامنه‌ی تولید، IP تولید) و نبودن کانتینرهای دیگر، اجرا نمی‌شود.

## معیار موفقیت (همه باید برقرار باشد)
- [ ] کل فرایند فقط با مواد «خارج از سرور» انجام شد (هیچ فایلی از سرور تولید کپی نشد)
- [ ] `backup-decrypt.mjs --verify` برای `_control` و هر تننت بازیابی‌شده موفق بود (کلید درست و فایل سالم)
- [ ] `GET /api/health` → `{"ok":true}` بعد از بالا آمدن stack
- [ ] تعداد تننت‌های ACTIVE در کنترل = عدد پنل ادمین تولید (یا اختلاف توجیه‌شده)
- [ ] تعداد `users` حداقل یک تننت واقعی = عدد تولید در لحظه‌ی بکاپ (`--expect slug=N`)
- [ ] ورود موفق به پنل ادمین و یک تننت؛ آخرین فاکتور/گزارش باز می‌شود
- [ ] **RTO اندازه‌گیری‌شده ≤ ۴ ساعت** (هدف ‏`disaster-recovery.md`)؛ هدف مطلوب ≤ ۲ ساعت
- [ ] فاصله‌ی تازگی داده (RPO) = اختلاف «الان» و تاریخ آخرین فایل S3 ≤ ۲۶ ساعت
- [ ] هیچ پیامک/پرداخت/ارسال خارجی واقعی از VM تمرین رفت (کلیدهای SMS/Zarinpal/S3 در `.env` تمرین خالی شده‌اند)
- [ ] VM در پایان **نابود** شد (ثبت زمان نابودی)

## چه چیزی باید خارج از سرور باشد (فقط نام‌ها — مقدارها هرگز در git/مستندات)
در password manager + یک کپی آفلاین رمزشده، **نه** روی همان سرور و نه فقط روی S3:
- `BACKUP_ENCRYPTION_KEY` (مهم‌ترین؛ بدون آن همه‌ی بکاپ‌ها بی‌مصرف‌اند)
- `POSTGRES_PASSWORD`، `JWT_SECRET`، `TAX_SECRETS_KEY`
- `LICENSE_KEY`، `LICENSE_PUBLIC_KEY_PEM`، (در صورت وجود) `LICENSE_SIGNING_PRIVATE_KEY_PEM` و فایل‌های `apps/backend-core/keys/*.pem`
- `BACKUP_S3_BUCKET`، `BACKUP_S3_ENDPOINT`، `BACKUP_S3_REGION`، `BACKUP_S3_ACCESS_KEY_ID`، `BACKUP_S3_SECRET_ACCESS_KEY` + **یک کلید S3 فقط‌خواندنی جداگانه برای تمرین**
- `EXIR_SMS_API_KEY`، `EXIR_SMS_SENDER_LINE`، `ZARINPAL_MERCHANT_ID`، `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`، `BAHA24_API_KEY`
- `ON_PREM_OWNER_PHONE`، `ON_PREM_OWNER_NAME`، `ON_PREM_ORG_NAME` و بقیه‌ی متغیرهای الزامی compose
- `INTERNAL_ALERT_TOKEN`، `MONITOR_ALERT_PHONE` (تازه؛ برای بازسازی پایش)
- دسترسی به مخزن git (deploy key فقط‌خواندنی)، DNS/CDN (چه کسی می‌تواند رکورد را عوض کند)، پنل میزبان/ارائه‌دهنده‌ی VM، کلیدهای SSH ادمین
- کپی رمزشده‌ی کل `.env` تولید (به‌روز؛ **تاریخ آخرین به‌روزرسانی را در همین جدول بنویسید**)

> نکته‌ی رایج شکست: `.env` خارج از سرور قدیمی است (کلید جدیدی بعد از آن اضافه/چرخانده شده). تمرین دقیقاً همین را آشکار می‌کند.

## قبل از شروع (۲۰ دقیقه، روی لپ‌تاپ)
1. از پنل ادمین تولید یادداشت کنید: تعداد تننت‌های فعال، تعداد کاربران یک تننت نمونه (`slug=N`)، تاریخ آخرین بکاپ هر دو، حجم آخرین فایل‌ها.
2. کلید فقط‌خواندنی S3 بسازید (`s3:GetObject`, `s3:ListBucket`) — اگر ارائه‌دهنده اجازه می‌دهد؛ در غیر این صورت کلید اصلی را موقتاً به‌کار ببرید و بعد بچرخانید.
3. یک VM آزمایشی **Ubuntu 24.04** بسازید (cloud trial: ۴ vCPU / ۸ GB RAM / ۱۰۰ GB دیسک؛ ترجیحاً شهر/ارائه‌دهنده‌ای غیر از تولید). ساعت ساخت را یادداشت کنید (`T_vm`).
4. فایل `.env` از محل خارج از سرور را روی VM بگذارید (`scp`؛ mode 600): `/root/prod.env.from-offbox`.

## اجرا (زمان‌بندی‌شده؛ سقف کل ۳ ساعت)
| زمان | کار |
|---|---|
| 0:00 | ساعت‌گیری را شروع کنید (`T0`). `hostnamectl set-hostname exir-drill-1` |
| 0:05 | export متغیرهای `DRILL_*` (بالای `scripts/drill/rebuild-drill.sh`) و **dry-run**: `./rebuild-drill.sh --env-file /root/prod.env.from-offbox` — خروجی را بخوانید؛ هر «REFUSED» یعنی ماشین اشتباه است |
| 0:10 | `./rebuild-drill.sh --env-file ... --expect <slug>=<N> --execute` |
| 0:10–1:30 | مراحل ۱ تا ۸ خودکار (نصب docker، کلون، `.env` خنثی‌شده، postgres، دانلود+بازیابی کنترل و تننت‌ها، build و start، راستی‌آزمایی) |
| 1:30–2:00 | چک‌های دستی (مرحله ۹): تونل SSH، ورود ادمین و تننت، دیدن یک فاکتور |
| 2:00 | `T1` = آخرین چک دستی. **RTO = (T1 − T0) + زمان ساخت VM**. فایل `drill-results-*.md` را بردارید |
| 2:10 | `--wipe` (اگر لازم) و **VM را از کنسول ارائه‌دهنده حذف کنید**؛ کلید S3 فقط‌خواندنی را ابطال/بچرخانید |

اگر مرحله‌ای شکست خورد: **متوقف نشوید** — علت را یادداشت کنید، اصلاح دستی کنید، زمان اصلاح را جدا بنویسید. شکست‌ها خروجی اصلی تمرین‌اند.

### اسکریپت چه می‌کند (و چه نمی‌کند)
- بدون `--execute` فقط guardها و برنامه را چاپ می‌کند. هیچ‌چیز نصب/دانلود نمی‌شود.
- `.env` تمرین از روی نسخه‌ی خارج از سرور ساخته می‌شود ولی **کلیدهای SMS، پرداخت، push و S3 خالی** و `MONITOR_DISABLED=true`، پورت‌ها فقط روی `127.0.0.1`. (دانلود S3 با کلید مستقل `DRILL_S3_*` و `rclone` انجام می‌شود تا خودِ stack هرگز به باکت تولید دست نزند و بکاپ/prune روی آن نکند.)
- کلید رمزنگاری فقط در یک فایل موقت mode 600 قرار می‌گیرد (نه در آرگومان خط فرمان).
- مرحله‌ی restore از همان `scripts/restore-control.sh` و `restore-tenant.sh` استفاده می‌کند (اول dry-run صحت‌سنجی کامل، بعد `--yes`).
- **نمی‌تواند** VM را بسازد/نابود کند، DNS را عوض کند، یا ورود OTP را خودکار تست کند (OTP پیامکی است) — این‌ها دستی‌اند.

## نکات و دام‌های شناخته‌شده
- **نقش‌های دیتابیس هر تننت** (کار در حال انجام: `scripts/tenant-db-roles`): اگر فعال شود، بعد از restore ممکن است لازم باشد نقش/رمز هر تننت دوباره ساخته شود. در تمرین بعدی این مرحله را به اسکریپت اضافه و زمانش را ثبت کنید.
- بکاپ‌ها با `pg_dump` ۱۸ گرفته می‌شوند و سرور Postgres ۱۶ است؛ سطر `SET transaction_timeout` توسط restore حذف می‌شود (در کد هست) — اگر نسخه‌ی image عوض شد دوباره بررسی کنید.
- build ایمیج‌ها بیشترین زمان را می‌برد؛ اگر RTO زیاد است، ایمیج‌ها را در registry خصوصی نگه دارید (اقدام بهبود).
- کنترل را **قبل از** بالا آمدن backend بازیابی کنید (اسکریپت همین ترتیب را دارد)؛ migrationها در entrypoint backend روی دیتابیس‌های بازیابی‌شده اجرا می‌شوند — اگر دیتابیس بکاپ از نسخه‌ی قدیمی‌تر کد باشد، migrate لازم است و زمان می‌برد.
- اگر دامنه/TLS تولید را به VM تمرین اشاره دهید، تمرین به «تولید دوم» تبدیل می‌شود. **نکنید**؛ تست فقط با تونل SSH.
