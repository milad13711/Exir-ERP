# ارجاع سند (Document Referral)

ارجاع عمومی روی هر موجودیت: یک سند را به یک کارشناس «ارجاع» می‌دهید، او اعلان می‌گیرد، همان سند را می‌بیند و اقدام می‌کند.

## مدل

`DocumentReferral` (جدول `document_referrals`، migration `20261107200000_document_referrals`، صفحه‌ی تننت، بدون FK چندریخت):

| فیلد | توضیح |
| --- | --- |
| `entityType` / `entityId` | نام پیوست‌ها (`SalesInvoice`، `SalesQuotation`، `PurchaseOrder`، `CrmContact`، `CrmDeal`، `Proposal`، `Contract`، `Project`، `Report`) |
| `fromUserId` / `toUserId` | ارجاع‌دهنده / گیرنده (ثبت‌شده در ownership-registry: `toUserId` انتقال‌پذیر، بقیه تاریخی) |
| `status` (TEXT) | `PENDING` → `ACCEPTED` → `DONE`؛ یا `RETURNED`، `CANCELLED`، `FORWARDED` (ارجاع مجدد) |
| `note`, `dueAt`, `acceptedAt`, `resolvedAt/By/Note` | یادداشت، موعد، زمان‌ها |
| `idempotencyKey` | کلید یکتا برای تکرار امن |

**مسئول پیگیری فعلی** = جدیدترین ارجاع فعال (`PENDING`/`ACCEPTED`) روی سند؛ ارجاع‌های اضافه (`additional: true`) «همکار» هستند. **تاریخچه** = همه‌ی ردیف‌های سند به ترتیب زمان.

## API (`/api/referrals`، فقط JWT؛ دسترسی داخل سرویس)

- `POST /referrals` — `{entityType, entityId, toUserId, note?, dueAt?, additional?, idempotencyKey?}`
- `POST /referrals/:id/accept | return | complete | cancel` — `{note?}`
- `POST /referrals/:id/reassign` — `{toUserId, note?, dueAt?}`
- `GET /referrals/inbox?view=active|done|sent|all`، `GET /referrals/counts`
- `GET /referrals/entity/:type/:id` — مسئول فعلی، همکاران، تاریخچه، `canRefer`
- `GET /referrals/assignees?entityType&ids=a,b` — ستون «مسئول» فهرست‌ها (فقط برای سندهای قابل‌دید)
- `GET /referrals/mine-ids?entityType` — فیلتر «ارجاع‌های من»

### چه کسی می‌تواند ارجاع دهد
مدیر (OWNER/ADMIN)؛ دارنده‌ی «ویرایش» ماژول سند (به شرط اینکه سند در دید عادی‌اش باشد)؛ صاحب سند؛ مسئول فعلی (ارجاع مجدد)؛ مدیر بالادستِ صاحب/مسئول در چارت سازمانی. بقیه ۴۰۳؛ سندِ خارج از دید ۴۰۴ (بدون افشا).

### اعلان
`NotificationsService.notify` با دسته‌ی `approvals`، `important: true`، عنوان «`فاکتور 123 به شما ارجاع شد`» و لینک `/referrals/view?type=…&id=…`. هیچ مسیر پیامکی جدیدی ساخته نشده؛ پیامک فقط همان «پیامک جایگزین» موجود کاربر است (در صورت روشن‌بودن ترجیح خودش و نرسیدن پوش). پذیرش/برگشت/انجام به ارجاع‌دهنده، لغو و ارجاع مجدد به مسئول قبلی اعلان می‌دهد.

## دسترسی به سند (Access grant)

`src/referrals/referral-grants.ts` — دو سطح، بدون جدول دسترسی (از ردیف‌های ارجاع/وظیفه مشتق می‌شود؛ ایندکس `(toUserId,status)` و `(entityType,entityId,status)`):

| وضعیت | مشاهده (سند + PDF + پیوست) | ویرایش محتوای سند |
| --- | --- | --- |
| ارجاع `PENDING`/`ACCEPTED` | بله | بله |
| وظیفه‌ی باز و منتشرشده (نه `APPROVED/CANCELLED/EXPIRED`) | بله | **هرگز** (وظیفه فقط مشاهده می‌دهد) |
| ارجاع `DONE` | **بله، دائمی (فقط‌خواندنی)** | خیر |
| `RETURNED` / `CANCELLED` / `FORWARDED` / `REVOKED` / وظیفه‌ی بسته (`APPROVED/CANCELLED/EXPIRED`) | خیر | خیر |

- **مشاهده:** `PermissionsService.viewScopeGranted` / `scopeWithGrants` (با `AND:[{OR:[…]}]`) روی مسیرهای خواندن: فهرست/جزئیات/PDF/تاریخچه‌ی نسخه/وضعیت امضا و پیوست‌ها (`read`).
- **ویرایش:** `PermissionsService.hasEditGrant(ctx, entityType, id)` / `editScopeGranted` فقط روی مسیرهای ویرایش محتوا: `PUT` فاکتور، `PATCH` پیش‌فاکتور، `PUT` سفارش خرید، `PUT` مشتری، `PATCH` فرصت، `PATCH` پیشنهاد، `PATCH` قرارداد، `PATCH` پروژه (بدون تغییر اعضای تیم)، `PATCH` گزارش، و افزودن/حذف پیوست همان سند. گیرنده برای این مسیرها به مجوز «ویرایش» ماژول نیاز ندارد.
- **قواعد وضعیت سند دست‌نخورده می‌ماند** (در سرویس‌ها): فقط فاکتور/سفارش/قرارداد پیش‌نویس ویرایش می‌شود؛ صادرشده/امضاشده/قفل‌شده/دوره‌ی بسته از مسیر اصلاح/ابطال موجود می‌گذرد؛ پروپوزال پذیرفته‌شده پیوست‌پذیر نیست.
- **هرگز از ارجاع مجاز نمی‌شود:** حذف، ابطال/لغو، تأیید و صدور (confirm)، پرداخت، امضا، تصمیم تأیید، تغییر مرحله‌ی فرصت، تغییر دسترسی/اعضا. این مسیرها همان `assertEdit/assertDelete` + `viewScope` سخت‌گیر را می‌خواهند.
- ارجاع‌های فعال با `additional:true` (همکار) همین حقوق را دارند؛ ارجاع جدید بدون آن، مسئول قبلی را `FORWARDED` می‌کند و هر دو سطح دسترسی او بسته می‌شود.
- نشان روی سند: مسئول فعلی «مسئول پیگیری: X»؛ اگر مسئول فعالی نیست و آخرین ارجاع `DONE` است «انجام‌شده توسط X · زمان».

سازنده‌ی وظیفه هنگام پیوند وظیفه به سند باید خودش سند را ببیند (یا مسئول فعال ارجاع آن باشد)؛ وگرنه ۴۰۳ (`task-link.ts`) — چون وظیفه‌ی پیوندخورده هم اکنون دسترسی ویرایش می‌دهد.

## رابط کاربری
- `<ReferralPanel entityType entityId />` — نشان «مسئول پیگیری»، دکمه‌ی «ارجاع»، تاریخچه، پذیرش/برگشت/انجام. روی جزئیات فاکتور، پیش‌فاکتور، سفارش خرید، فرصت/مشتری CRM، پیشنهاد، قرارداد، پروژه و گزارش (شامل دانش سازمانی).
- `/referrals` — «ارجاع‌های من» با شمارنده‌ها؛ `/referrals/view?type&id` — نمایش سند مستقل از ماژول (برای گیرنده‌ای که ماژول مبدأ را در منو ندارد).
- فهرست فاکتورها: ستون «مسئول» و فیلتر «ارجاع‌های من».
- جزئیات وظیفه: «سند مرتبط … مشاهده‌ی سند».

## گزارش‌ها (دانش سازمانی)
ارجاع قدیمی گزارش (`ReportReferral`، چندنفره و پاراف) حفظ شد و حالا هم‌زمان ارجاع عمومی می‌سازد: اعلان با دسته‌ی ارجاع و لینک مستقیم، دسترسی به همان گزارش حتی بدون دسترسی ماژول گزارش‌ها، ورود به «ارجاع‌های من»؛ پاراف = «انجام شد».

## افزودن نوع جدید
یک ورودی در `src/referrals/entity-defs.ts` + استفاده از `viewScopeGranted`/`scopeWithGrants` در مسیرهای خواندن کنترلر + یک case در `app/(app)/referrals/view/page.tsx` + `<ReferralPanel>` در مودال سند.

## سخت‌سازی (بازبینی امنیتی ۱۴۰۵/۰۸)
- **شکل scope:** حالت «فقط ارجاع‌ها» `{AND:[{id:{in}}]}` است تا `{ id, ...scope }` شناسه‌ی درخواستی را بازنویسی نکند؛ سقف شناسه ۵۰۰۰ با ترتیب قطعی و هشدار در لاگ هنگام برش.
- **ویرایش فقط از ارجاع فعال**؛ پیوست افزودن/حذف با ارجاع فقط روی سند غیرقفل (`editableWhen` در `entity-defs.ts`: فاکتور/پیش‌فاکتور/سفارش/قرارداد = DRAFT، پروژه ≠ تکمیل/لغو، فرصت ≠ WON/LOST، پیشنهاد = DRAFT/REVISION_REQUESTED).
- **فیلدهای دسترسی در ویرایش با ارجاع حذف می‌شوند:** `managerUserId`/`memberUserIds` پروژه، `referredSignerUserId` قرارداد، `assignedUserId` پیشنهاد؛ تغییر `contactId/dealId/supplierId` فقط اگر در دامنه‌ی سخت‌گیر CRM ویرایشگر باشد (`grant-edit.ts`).
- **وظیفه‌ی تکرارشونده** پیوند به سندِ قابل‌ارجاع را کپی نمی‌کند (کرون کاربر ندارد تا `assertTaskLinkAllowed` اجرا شود). پیوند `Shipment` فقط برای دارندگان دید ماژول dispatch.
- **لغو دسترسی ارجاع انجام‌شده:** `POST /referrals/:id/revoke` (وضعیت `REVOKED`) برای مدیر یا مدیر بالادستِ ارجاع‌دهنده، بدون اعلان، با ممیزی؛ دکمه‌ی «لغو دسترسی» در تاریخچه‌ی پنل.
- **هم‌زمانی:** migration `20261107210000_document_referral_concurrency` — ستون `isPrimary` و دو ایندکس یکتای جزئی (یک ارجاع فعالِ اصلی برای هر سند؛ یک ارجاع فعال برای هر گیرنده). خطای P2002 (کلید تکرار/رقابت) نتیجه‌ی موجود را برمی‌گرداند یا یک بار تلاش مجدد می‌کند. ایندکس‌های جزئی در schema.prisma قابل‌بیان نیستند (فقط SQL).
